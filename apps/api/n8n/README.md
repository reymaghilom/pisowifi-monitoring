# n8n workflow: PisoWiFi status notifications

> **v4 is current:** `pisowifi-status-workflow.v4.json`, generated by `build-workflow-v4.mjs`. It adds:
> - approved machine and recipient lists (IDs only);
> - insert-ordered reservations, so concurrent duplicates cannot both send;
> - a chronology guard;
> - timestamp-window checks;
> - `[PisoWiFi Alert]` / `[PisoWiFi Recovery]` wording with Previous and Current Status and downtime;
> - no credential placeholders.
>
> Setup, tests and the Gmail network requirement are in `docs/operations/n8n-v4-gmail-setup.md`. The v3 description
> below is kept for reference; the v3 file is unchanged.

`pisowifi-status-workflow.json` (**v3**, N1-B2) implements the webhook contract in `apps/api/README.md`
("Status-change notifications (n8n → Gmail)"). Earlier versions are kept for review only:
`pisowifi-status-workflow.v2-n1b.json` (single recipient) and `pisowifi-status-workflow.v1-original.json` (loses
alerts when Gmail fails).

```
Webhook → Valid Event? → Load Delivery State → Plan → Anything To Send?
            └ 400          (per event)          │        ├ no  → Respond Nothing To Send (200 duplicate / 503 in progress)
                                                 │        └ yes → Split Recipients → Each Recipient (loop, 1 at a time)
                                                 │                  loop: Reserve "sending" → Send Gmail → Record "sent" / "failed" → Outcome
                                                 │                  done: Summarize → Respond Result (200 all done / 503 otherwise)
```

## What it guarantees, and what it does not

- **Recipients come from the backend.** The payload carries `recipients: [{id, email}]`, resolved by the API when
  the change is recorded: every active account (today the two Administrators and the Member), minus per-kind
  opt-outs in `notification_prefs`. The template contains no addresses.
- **Per-recipient delivery state**, in the n8n Data Table `pisowifi_alert_deliveries`, keyed by event ID + recipient
  **user ID**. Addresses are never stored there.
  - Before each send, a `sending` reservation is written.
  - After the send, the row is marked `sent` or `failed`.
  - An event is complete only when every recipient is `sent`.
- **Partial failures.** Recipients that failed get 503 back to PisoWiFi, which retries with the same event ID. A retry
  emails only the recipients that are not yet `sent`; this also holds after an n8n crash and restart, because the
  state is on disk.
- **Ambiguous timeouts are minimised, not eliminated.**
  - A `sending` row younger than 2 minutes means an earlier run may still be sending. That recipient is deferred
    (503), not emailed again, and the others still go out.
  - After 2 minutes the earlier run is certainly over: n8n stops every run at 25 s. If its result was never recorded,
    nobody can know whether the provider accepted the email, so the recipient is emailed again.
  - That is the one case that can produce a duplicate. It needs n8n to die or time out between the Gmail call and
    the record write. Delivery is therefore **at-least-once, not exactly-once**.
- **Node-level Gmail retry is off.** An in-execution retry after a timeout could resend; retries come from PisoWiFi
  (30 s, 1 min, 2 min … 12 attempts).
- **Wording comes from contract fields.**
  - Subject: "PisoWiFi alert: <machine> is **Offline**" or "PisoWiFi: <machine> is **Back Online**".
  - Body: machine name, IP, "Status: Offline / Back Online", the payload's Asia/Manila date/time, and the event ID.
  - `status` / `previousStatus` stay `Reachable` / `Unreachable` and are validated as such.
- **Privacy.**
  - Responses carry counts only. The workflow saves no execution data, and no addresses reach the n8n log.
  - n8n still keeps a run's data, including the webhook body, while the run is in progress. With
    `EXECUTIONS_DATA_HARD_DELETE_BUFFER=0` and `EXECUTIONS_DATA_PRUNE_HARD_DELETE_INTERVAL=1` (in
    `deploy/n8n/config/n8n.env`), it is removed within about a minute; measured: 10 s.
  - Bytes of deleted rows can linger in SQLite free pages and the WAL until they are overwritten. Backups use
    `VACUUM INTO`, which leaves them behind.

| Response | HTTP | PisoWiFi dispatcher |
|---|---|---|
| all recipients sent now or earlier | 200 `sent` / `duplicate` | marks the delivery `sent` |
| some failed, or one may still be in flight | 503 `partial` / `in_progress` | retries (only pending recipients are emailed) |
| bad/missing webhook auth | 403 | retries, logs a credentials hint |
| invalid payload (incl. recipients: 1–20, unique ids, address format) | 400 | retries, then `failed` |
| run exceeded 25 s | 500 | retries |

## Set up (N1-F, needs approval)

1. Create the **Data table** `pisowifi_alert_deliveries`, with all columns of type *string*: `event_id`,
   `recipient_id`, `event`, `status`, `attempted_at`, `sent_at`.
2. Create the credentials:
   - **Header Auth** "PisoWiFi Webhook Auth": Name `Authorization`, Value `Bearer <N8N_WEBHOOK_SECRET>`, created
     without displaying the secret.
   - **Gmail OAuth2** "PisoWiFi Gmail (send only)":
     - Google Cloud OAuth client (Web application) with scope `https://www.googleapis.com/auth/gmail.send`.
     - Redirect `http://localhost:5678/rest/oauth2-credential/callback` (through the IAP tunnel).
     - Consent screen **In production**; in *Testing*, refresh tokens expire after 7 days.
3. Import the JSON, select both credentials, and save it **inactive**. No address needs to be entered: recipients
   come from the payload.
4. The dispatcher must use `N8N_TIMEOUT_MS=30000` (longer than the 25 s execution timeout).

Tests: `deploy/n8n/tests/workflow-e2e.mts` runs this exact file with only two changes, both asserted: Gmail is swapped
for a local mail sink, and the in-flight window is 45 s instead of 120 s.
